# Architecture

## Overview

Streamlit handles interaction, PyPDF extracts page text, Ollama creates
embeddings and answers questions, and ChromaDB stores vectors and metadata.
Local development uses local Ollama and a `PersistentClient` under
`chroma_db/`. Cloud deployment can connect to a remote Ollama service and a
remote Chroma HTTP server backed by durable storage.

```text
Upload PDF
  -> validate extension/size
  -> PyPDF page extraction
  -> page-aware text chunks
  -> Ollama nomic-embed-text
  -> local PersistentClient or configured remote Chroma HTTP server
  -> per-chunk embedding-model metadata

Question
  -> question embedding
  -> cosine similarity retrieval from the same Chroma collection
  -> empirically calibrated distance cutoff and result limit
  -> Ollama llama3.2:3b with retrieved context and a structured answer response
  -> answer, retrieved source pages, supporting passages
```

## Modules

| Module | Responsibility |
| --- | --- |
| `app.py` | Streamlit interface, service/model status, uploads, index/remove, questions |
| `app_services.py` | Resolve local/remote service configuration, index PDFs, construct services |
| `document_loader.py` | Validate and extract readable PDF pages with PyPDF |
| `chunker.py` | Split each page into chunks with source/page metadata |
| `embeddings.py` | Request real vectors from Ollama; errors do not trigger fake vectors |
| `vector_store.py` | Local/remote Chroma clients, metadata, searching, duplicate IDs, deletion |
| `retriever.py` | Embed question, query Chroma, filter by cosine distance |
| `llm_service.py` | Grounded prompt and local chat-model call |
| `rag_service.py` | Coordinate retrieval and answer/refusal behavior |
| `evaluate.py`, `evaluation.py` | Run the question set and calculate reported metrics |

## Storage and metadata

The Chroma collection is named `college_documents`, uses cosine distance, and
stores a chunk's text with its source filename, 1-based page number, chunk
index, document ID, and embedding model. A document ID is the SHA-256 of the
complete PDF bytes. Re-uploading identical bytes is skipped by the UI; Chroma
upserts also use deterministic per-chunk IDs. Removing a document deletes all
chunks matching its document ID. Local Chroma persists on the local disk.
The remote HTTP client stores data on the Chroma server; persistence across
Streamlit restarts requires that server's data directory to be mounted on
durable storage. Streamlit Cloud's application filesystem is not persistent.
The shared public collection is visible/removable by all app visitors; do not
index confidential documents.

Untagged legacy chunks are re-embedded from their stored text with
`nomic-embed-text` before search or adding documents. If stored vectors have an
incompatible dimension, the app blocks retrieval and reports the need to
re-index from the original PDFs. Do not manually edit Chroma files while the
application is open.

## Grounding and limitations

The model must return a structured answerability flag and answer. The app
converts every unsupported result to the exact configured refusal. Retrieval
drops passages whose cosine distance exceeds the 0.64 cutoff. This value
preserves all answerable retrievals in the bundled 50-question test set (the
largest measured answerable distance was 0.6331); semantically related
unanswerable questions can still retrieve context, so the model's grounding
decision remains necessary. Retrieved source metadata is rendered from Chroma,
not generated by the LLM.

Prompting and similarity filtering are not a formal proof that every generated
sentence is entailed by evidence. Users must verify important answers in the
displayed passages and original PDF. OCR and per-user access control are not
implemented. The web app supports HTTPS remote Ollama/Chroma endpoints; the
MCP server remains a local stdio integration.
